# História de Usuário

EU COMO Autor, Editor Técnico ou Administrador de Conteúdo da plataforma Docs-Wiki,  
GOSTARIA DE criar novos materiais técnicos no padrão OKF, publicar novas versões incrementais diretas, resolver conflitos de concorrência otimista (OCC) e executar rollbacks lineares não-destrutivos,  
PARA QUE eu possa evoluir e versionar a base de conhecimento com total integridade criptográfica SHA-256, consistência em edições concorrentes e histórico imutável.  

# Escopo

- Criação de novos materiais técnicos via 'POST /api/v1/content/materials' com validação rigorosa de frontmatter YAML (gray-matter) e schema Zod, verificação de slug único e gravação da versão inicial (versão 1) com hash SHA-256.
- Publicação incremental direta de novas versões ('POST /api/v1/content/materials/:id/versions') validando 'parent_version_id === versao_head_id' via bloqueio transacional 'SELECT FOR UPDATE' e incrementando sequencialmente 'versao_num = MAX + 1'.
- Tratamento de conflito de concorrência otimista (OCC) com retorno imediato de 'HTTP 409 Conflict' quando 'parent_version_id != versao_head_id', viabilizando recarregamento do HEAD e resolução de conflito em loop.
- Rollback seguro não-destrutivo via 'POST /api/v1/content/materials/:id/rollback', criando uma nova versão (MAX + 1) com o snapshot da versão K alvo e preservando a integridade de todas as versões anteriores.
- Emissão assíncrona de eventos transacionais via RabbitMQ ('material.criado' e 'material.atualizado') para indexação vetorial e geração de embeddings no nlp-service.

# Não Escopo

- Resolução de conflitos tridirecionais automáticos (3-way merge no estilo Git merge) ou criação de branches paralelas / forks de documentos nesta fase.
- Exclusão física destrutiva de versões históricas específicas dentro do histórico do documento.
- Edição colaborativa em tempo real com Operational Transformation (OT) ou CRDTs (estilo Google Docs).

# Critérios de Aceite

**CA01 - Criação de Novo Material OKF com Sucesso [Cobre: SC-003]**  
- **Dado** que um editor autenticado submete um novo documento no formato OKF com slug único e metadados válidos  
- **Quando** a requisição atingir 'POST /api/v1/content/materials'  
- **Então** o sistema deve abrir transação no PostgreSQL, calcular o hash SHA-256 do conteúdo, inserir o material com versão 1, definir a versão HEAD e retornar status 'HTTP 201 Created'  
- **E** publicar o evento 'material.criado' na exchange do RabbitMQ para processamento de NLP  

**CA02 - Rejeição de Criação por Sintaxe YAML ou Frontmatter Inválido [Cobre: SC-006]**  
- **Dado** que o usuário envia um documento com formatação YAML corrompida ou campos obrigatórios ausentes no frontmatter  
- **Quando** o parser OKF e o schema Zod 'CreateMaterialDTOSchema' processarem a entrada  
- **Então** o backend deve abortar a operação e retornar status 'HTTP 400 Bad Request'  
- **E** detalhar na resposta os erros de sintaxe ou campos inválidos encontrados  

**CA03 - Rejeição de Criação por Slug Duplicado [Cobre: SC-002]**  
- **Dado** que o documento submetido possui um slug que já existe cadastrado na tabela 'conteudo.materiais'  
- **Quando** a verificação de unicidade consultar o banco de dados  
- **Então** o sistema deve rejeitar a criação retornando status 'HTTP 400 Bad Request'  
- **E** informar que o slug já está em uso por outro material  

**CA04 - Publicação Direta de Nova Versão com HEAD Válido [Cobre: SC-004]**  
- **Dado** que o editor submete uma nova versão informando 'parent_version_id' exatamente igual ao 'versao_head_id' atual do material  
- **Quando** o endpoint 'POST /api/v1/content/materials/:id/versions' processar a transação com 'SELECT FOR UPDATE'  
- **Então** o sistema calcula o novo SHA-256, grava a nova versão com 'versao_num = MAX + 1', atualiza 'versao_head_id' na tabela 'conteudo.materiais' e comita a transação com status 'HTTP 201 Created'  
- **E** publica o evento 'material.atualizado' na exchange do RabbitMQ  

**CA05 - Detecção de Conflito de Concorrência Otimista (OCC) e Resolução [Cobre: SC-007]**  
- **Dado** que dois editores tentam salvar modificações concorrentes sobre a mesma versão base de um material  
- **Quando** o segundo commit for enviado com 'parent_version_id' diferente do 'versao_head_id' atual  
- **Então** a transação com 'SELECT FOR UPDATE' deve sofrer ROLLBACK e retornar status 'HTTP 409 Conflict'  
- **E** a interface deve exibir alerta de conflito e permitir ao editor recarregar a versão HEAD para resolver as diferenças e comitar com sucesso  

**CA06 - Rollback Seguro Não-Destrutivo para Versão Anterior [Cobre: SC-001]**  
- **Dado** que um administrador ou editor autorizado solicita a restauração da versão histórica K de um material  
- **Quando** a requisição for enviada para 'POST /api/v1/content/materials/:id/rollback'  
- **Então** o sistema deve copiar o snapshot da versão K, criar uma nova versão (MAX + 1), apontar a versão HEAD para este novo registro e retornar 'HTTP 201 Created'  
- **E** publicar o evento 'material.atualizado' no RabbitMQ sem deletar nenhum registro anterior do histórico  

**CA07 - Rejeição de Rollback por Versão Alvo Inexistente [Cobre: SC-005]**  
- **Dado** que o usuário solicita rollback especificando um número de versão K que não consta no histórico  
- **Quando** a consulta buscar a versão na tabela 'conteudo.material_versoes'  
- **Então** o sistema deve rejeitar o rollback retornando status 'HTTP 404 Not Found'  
- **E** informar que a versão alvo informada não existe para este material
