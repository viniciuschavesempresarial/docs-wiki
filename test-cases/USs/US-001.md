# História de Usuário

EU COMO Usuário da plataforma Docs-Wiki (Visitante, Leitor, Editor ou Administrador),  
GOSTARIA DE realizar meu auto-cadastro seguro, autenticar minhas credenciais na API de IAM e navegar pelo catálogo e rotas administrativas protegidas,  
PARA QUE eu possa acessar recursos técnicos condizentes com o meu nível de permissão (RBAC), garantindo a proteção e integridade dos dados da aplicação.  

# Escopo

- Interface e endpoints de auto-registro (/register e POST /api/v1/auth/register) com validação Zod client/server-side de campos obrigatórios (nome >= 3 chars, e-mail válido, senha forte >= 8 chars contendo ao menos uma letra e um número).
- Mecanismo de proteção contra força bruta e DoS com Rate Limiting duplo na borda NGINX (5 req/s) e middleware Express no iam-service.
- Armazenamento seguro de senhas com algoritmo Bcrypt utilizando fator de custo de 12 rounds de salt e atribuição automática da role inicial 'LEITOR' para novas contas.
- Fluxo de autenticação (/login e POST /api/v1/auth/login) com validação de status ativo do usuário, comparação criptográfica de senha e emissão de JWT com validade de 8 horas persistido em cookie seguro (HttpOnly, SameSite=Lax, Secure).
- Guarda de rotas no cliente (AuthGuard) e middleware de autorização RBAC no backend para controle de acesso às páginas sensíveis (/editor e /admin) com tratamento de erros 401 Unauthorized e 403 Forbidden.

# Não Escopo

- Recuperação de senha via e-mail (fluxo 'Esqueci minha senha') ou envio de links mágicos (Magic Links), que será implementado em versão futura.
- Autenticação federada OAuth 2.0 / OpenID Connect (Google, GitHub, GitLab) ou SSO corporativo SAML/LDAP.
- Autenticação multifator (MFA / 2FA) via TOTP ou SMS nesta primeira iteração da plataforma.

# Critérios de Aceite

**CA01 - Navegação e Acesso à Tela de Registro [Cobre: SC-002]**  
- **Dado** que um visitante não autenticado acessa a aplicação Docs-Wiki  
- **Quando** seleciona a opção de registrar uma nova conta  
- **Então** o sistema deve renderizar o formulário 'RegisterPage' na rota '/register'  
- **E** exibir os campos de entrada para 'nome', 'email' e 'password'  

**CA02 - Bloqueio por Excesso de Requisições - Rate Limit [Cobre: SC-006]**  
- **Dado** que um cliente dispara múltiplas requisições simultâneas para o endpoint de registro  
- **Quando** a taxa de requisições ultrapassar o limite configurado de 5 req/s no NGINX / Express  
- **Então** o gateway/servidor deve rejeitar a requisição imediatamente com status 'HTTP 429 Too Many Requests'  
- **E** interromper o processamento antes de atingir a camada de banco de dados  

**CA03 - Validação de Formato e Complexidade de Dados no Registro [Cobre: SC-008]**  
- **Dado** que o usuário submete o formulário de cadastro com dados inválidos (ex: nome curto, e-mail malformado ou senha sem letras/números)  
- **Quando** o schema Zod 'AuthRegisterDTOSchema' processar o payload  
- **Então** a API deve retornar 'HTTP 400 Bad Request'  
- **E** fornecer no corpo da resposta os detalhes específicos de validação de cada campo rejeitado  

**CA04 - Detecção de Conflito de E-mail Duplicado [Cobre: SC-001]**  
- **Dado** que o usuário preenche o cadastro com um e-mail já registrado na tabela 'iam.users'  
- **Quando** o serviço de IAM consultar a base de dados  
- **Então** o sistema deve rejeitar o cadastro retornando 'HTTP 409 Conflict'  
- **E** exibir mensagem informando que o e-mail já se encontra cadastrado  

**CA05 - Registro Bem-Sucedido e Hashing Criptográfico [Cobre: SC-004]**  
- **Dado** que o usuário envia dados válidos e um e-mail inédito  
- **Quando** o sistema processar a criação da conta  
- **Então** a senha deve ser criptografada com Bcrypt (12 rounds de salt), o usuário inserido no banco com role 'LEITOR' e retornado 'HTTP 201 Created'  
- **E** o usuário deve ser redirecionado para a página de Login (/login)  

**CA06 - Autenticação Rejeitada por Credenciais Incorretas [Cobre: SC-007]**  
- **Dado** que um usuário tenta autenticar com senha incorreta ou conta inativa na página de Login  
- **Quando** a verificação de hash Bcrypt falhar  
- **Então** a API deve retornar 'HTTP 401 Unauthorized'  
- **E** o frontend deve exibir a mensagem de erro 'Credenciais incorretas'  

**CA07 - Login com Sucesso e Emissão de Cookie HttpOnly [Cobre: SC-003]**  
- **Dado** que o usuário insere e-mail e senha corretos de uma conta ativa  
- **Quando** a autenticação for concluída com sucesso  
- **Então** o servidor deve emitir um token JWT com validade de 8 horas gravado no cookie HttpOnly 'token' (SameSite=Lax, Secure)  
- **E** redirecionar o usuário autenticado para a HomePage do Catálogo (/)  

**CA08 - Bloqueio de Acesso por Falta de Permissão RBAC [Cobre: SC-005]**  
- **Dado** que um usuário autenticado com perfil 'LEITOR' tenta acessar rotas restritas (/editor ou /admin)  
- **Quando** o 'AuthGuard' verificar que o usuário não possui a permissão requerida ('materials:create' ou 'admin:all')  
- **Então** o sistema deve bloquear a navegação e retornar 'HTTP 403 Forbidden / Acesso Negado'  
- **E** exibir aviso visual informando que o perfil atual não possui permissão para o recurso  

**CA09 - Acesso Autorizado a Recursos Protegidos [Cobre: SC-003]**  
- **Dado** que um usuário autenticado possui as roles adequadas ('EDITOR' ou 'ADMIN')  
- **Quando** navegar para a rota protegida (/editor ou /admin)  
- **Então** o 'AuthGuard' deve autorizar a renderização completa da página solicitada  
- **E** liberar os componentes e ações correspondentes ao perfil do usuário
